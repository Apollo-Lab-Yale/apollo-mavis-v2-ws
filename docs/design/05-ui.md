# 05 — apollo-xarm7-ui (React 18 + Vite + TypeScript SPA)

Status: v0.2 (2026-09-01, amended). Conforms to `00-overview.md` **v0.3**
(spine) and `docs/research/web-teleop-stack.md` (measured/verified facts).
This revision resolves all v0.1 open questions as **binding** decisions
(marked "Resolved/Confirmed" inline) and adds the direct joint-control panel
(§8.3), `start_from` session choice, initial-condition profile actions, and
inference-mode takeover semantics. The UI never
imports Python; it talks to `apollo-xarm7-runtime` exclusively over HTTP/WS on
a single origin (overview §1, §8). The UI is **never in the control path** —
it only reports held keys and discrete intents; all motion, safety gating and
watchdog logic live server-side (overview §6, §9).

Target browsers: desktop Chrome/Firefox on the operator machine (LAN/localhost,
single operator). `KeyboardEvent.code`, `createImageBitmap`, `OffscreenCanvas`
are all Baseline there; state this in the repo README.

### 1.1 Dev/prod serving

- **Prod**: `pnpm build` → `dist/`; runtime mounts it last as
  `StaticFiles(directory=..., html=True)` on `/` (overview §8, research §6.1).
  Hash routing means deep links never 404 against `StaticFiles`.
- **Dev**: Vite dev server with proxy (HMR); all app URLs are **relative**
  (same-origin), WS URLs derived from `location`:

```ts
// vite.config.ts (essentials)
export default defineConfig({
  plugins: [react()],
  server: {
    proxy: {
      "/api":   { target: process.env.APOLLO_RUNTIME_URL ?? "http://localhost:8765" },
      "/ws":    { target: process.env.APOLLO_RUNTIME_URL ?? "http://localhost:8765", ws: true },
      "/video": { target: process.env.APOLLO_RUNTIME_URL ?? "http://localhost:8765" },
    },
  },
});

// src/api/ws/url.ts helper
export const wsUrl = (path: string) =>
  `${location.protocol === "https:" ? "wss" : "ws"}://${location.host}${path}`;
```

**Confirmed (binding, spine v0.3)**: the runtime dev server listens on port
8765 — the proxy default above stands; prod is always same-origin.

## 2. Generated TypeScript types (pipeline)

Single source of truth: **pydantic models in `apollo_xarm7_core.protocol`**
(overview §8: "TS types generated from their JSON schema").

Pipeline (all outputs checked in so the UI builds with zero Python installed):

1. Core exports schemas: `python -m apollo_xarm7_core.protocol.export_schemas
   --out schemas/` writes JSON Schema (draft 2020-12, pydantic
   `model_json_schema()`) files into the core repo, checked in there.
2. `pnpm gen:sync` (`scripts/sync-schemas.ts`) copies
   `../apollo-xarm7-core/schemas/*.json` → `./schemas/` (vendored copy checked
   into the UI repo; fails loudly if the sibling checkout is missing).
3. `pnpm gen:types` (`scripts/gen-types.ts`) runs `json-schema-to-typescript`
   (`compileFromFile`, options `{ additionalProperties: false, bannerComment:
   "/* AUTO-GENERATED from apollo-xarm7-core schemas — do not edit. */" }`)
   producing `src/gen/*.ts`.
4. `pnpm gen:check` regenerates into a temp dir and `git diff --no-index`s
   against `src/gen/` + `schemas/` — run in CI so drift between core and UI is
   a build failure, not a runtime surprise.

Key generated types the rest of this doc uses (shapes shown as they will be
generated; authoritative source is core):

## 3. Routing

Hash routing (`createHashRouter`) because runtime serves the SPA via
`StaticFiles(html=True)`, which 404s deep paths (research §6.1). Routes:

```
#/            → Landing
#/teleop      → Teleop      (Cockpit)
#/collect     → Collect     (Cockpit)
#/dagger      → Dagger      (Cockpit)
#/inference   → Inference   (Cockpit)
#/devices     → Devices     (gamepad + tracker debug; NO session loader — 13-tracker §5)
```

A `sessionLoader` guard on all mode routes calls `GET /api/session`; if there is
no active session, or `session.mode` mismatches the route, it redirects to
`#/`. The landing page navigates to `#/<mode>` only after `POST /api/session`
returns 200. Epoch change detection (§5.1) also forces navigation to `#/`.

getWorkcell():   GET  /api/workcell        → WorkcellStatus

Episode start/save/discard and profile ops (`save_profile`,

the keys that trigger them; the server replies with `AckMsg` and the
authoritative state arrives via telemetry). Buttons and keys share this one
path. **Confirmed as designed (binding, spine v0.3).**

## 5. WebSocket clients

### 5.1 `ReconnectingWS` (`src/api/ws/reconnecting.ts`)

Bespoke ~40-line wrapper (research §1.3 recommends bespoke over
`reconnecting-websocket`). The `WebSocket` constructor is **injected** so tests
substitute `mock-socket`/fakes.

```ts
export type WsFactory = (url: string) => WebSocket;

export interface ReconnectingWsOpts {
  url: string;
  onMessage: (data: string | ArrayBuffer) => void;
  onStatus: (s: WsStatus) => void;
  binaryType?: "arraybuffer";
  wsFactory?: WsFactory;                    // default: (u) => new WebSocket(u)
  baseBackoffMs?: number;                   // 250
  maxBackoffMs?: number;                    // 5000
}
export class ReconnectingWS {
  constructor(opts: ReconnectingWsOpts);
  send(data: string | ArrayBufferLike): boolean;   // false (dropped) unless OPEN
  close(): void;                                    // permanent — cancels reconnect
}
```

Backoff: start 250 ms, full jitter (`delay = backoff + Math.random() *
backoff`), doubling to a 5 s cap; reset to 250 ms on successful open.
`onerror` → `ws.close()` so every failure funnels through `onclose`.

**Session-epoch resync** (research §1.3), implemented in the clients that use
the wrapper, not the wrapper itself:

- Control WS: server sends `HelloMsg{epoch, session_id, role}` first. The
  client compares against the epoch stored from `SessionInfo`. Mismatch ⇒ the
  runtime restarted mid-session: toast "Runtime restarted — session lost",
  clear the store, navigate to `#/`.
- On any control reconnect the client: (1) re-fetches `GET /api/session` to
  resync mode/episode state, (2) resets `seq` continuity expectations by
  starting from its monotonic counter (never resets to 0 within a page
  lifetime), (3) **always resumes from an all-keys-up state** — first message
  after `hello` is `{t:"keys", held: []}`; the pre-disconnect held set is never
  replayed. The capture surface is force-disarmed on control-WS loss.
- `role: "observer"` in hello (a second tab grabbed control first, research
  §1.4) ⇒ read-only banner "Another tab holds control"; capture disabled.
  **Confirmed as designed** (binding): the observer role — not a 1008 close —
  is how the runtime handles a second control connection.

### 5.2 `ControlClient` (`src/api/ws/control.ts`) — hybrid protocol sender

Implements the hybrid key protocol (overview §8, research §1.2): an immediate
`KeysMsg` on **every** transition plus a full-state heartbeat at **25 Hz**
(40 ms `setInterval`, running only while capture is armed). 25 Hz gives the
server's ~0.2 s watchdog 5 missed beats of margin. permessage-deflate is a
server-side setting; the client just sends compact JSON (~120 B ⇒ ~3 KB/s).

```ts
export class ControlClient {
  constructor(opts: {
    getHeld: () => ReadonlySet<string>;     // reads capture hook's ref — no React state
    onHello: (h: HelloMsg) => void;
    onAck: (a: AckMsg) => void;
    onStatus: (s: WsStatus) => void;
    wsFactory?: WsFactory;
  });
  connect(): void;                          // wsUrl("/ws/control")
  notifyTransition(): void;                 // capture hook calls on every down/up → immediate KeysMsg
  sendAction(name: ActionName, args?: Record<string, unknown>): void;
  setArmed(armed: boolean): void;           // starts/stops the 40 ms heartbeat;
                                            // disarm sends one final { held: [] }
  close(): void;
}
```

Rules:

- `seq` is a single monotonic counter across transitions and heartbeats.
- Disarming capture (click-away, Escape, blur, hidden tab, WS reconnect)
  synchronously attempts one `{held: []}` send before stopping the heartbeat.
  If the socket is down, the server watchdog covers it — the UI never assumes
  its empty-set message arrived.
- `held` contains only keymap entries with `kind === "held"`. Discrete keys
  (Tab/Space/N/Enter/Backspace) are sent as `ActionMsg` exactly once per
  physical press (§6). **Active arm is server-authoritative**: Tab sends
  `{t:"action", name:"switch_arm"}` with no argument; the server cycles and the
  new `active_arm` arrives via telemetry. The UI never locally predicts it.
- Background-tab timer throttling would starve the heartbeat, but
  `visibilitychange` disarms capture first (§6), so a throttled heartbeat can
  only ever be sending empty sets.

### 5.3 `TelemetryClient` (`src/api/ws/telemetry.ts`)

Read-only consumer of `/ws/telemetry` (20–30 Hz broadcast). Parses
`TelemetryMsg`, drops messages with `seq` ≤ last seen, and writes into the
zustand store via `store.setState` (imperative, outside React). It also stamps
`telemetryAt = performance.now()`; a 500 ms ticker sets `telemetryStale` when
`performance.now() - telemetryAt > 1000`. Telemetry reconnects independently
of control (separate `ReconnectingWS`); observers (no capture) still get full
telemetry.

### 5.4 `VideoStream` (`src/api/ws/video.ts`)

One WS per stream on `/ws/video/{stream_id}` (research §2.3: per-stream WS
reconnects independently; WS connections are exempt from the 6-per-origin
HTTP/1.1 pool). The server keeps a depth-1 latest-frame slot per client, so a
slow client drops frames rather than accumulating latency.

Binary frame layout (matches the server's `struct.pack("<dI", ts, len(jpeg)) +
jpeg`): **little-endian, 12-byte header** — `f64 ts_seconds` at offset 0,
`u32 jpeg_len` at offset 8, JPEG bytes from offset 12.

```ts
// src/lib/binary.ts — pure, unit-tested
export interface VideoFrameHeader { ts: number; len: number; payloadOffset: 12 }
export function parseFrameHeader(buf: ArrayBuffer): VideoFrameHeader;

// src/api/ws/video.ts
export class VideoStream {
  constructor(opts: {
    streamId: string;
    canvas: HTMLCanvasElement;
    onStats: (s: { staleMs: number; fps: number; latencyMs: number | null }) => void; // ≤4 Hz
    useWorker?: boolean;                    // §5.5
    wsFactory?: WsFactory;
  });
  start(): void;  stop(): void;
}
```

Main-thread render path (default): `binaryType = "arraybuffer"`; on message →
`parseFrameHeader` → `new Blob([view], {type: "image/jpeg"})` →
`await createImageBitmap(blob)` (decodes off the main thread) → `ctx.drawImage`
→ `bmp.close()`. A `decoding` flag drops incoming frames while a decode is in
flight (latest-wins on the client too). Canvas size is set once from the first
frame's bitmap dimensions.

**Stale-frame indicator**: staleness uses *arrival* time (`performance.now()`
of last drawn frame), threshold **500 ms** → grey overlay + "STALE" chip
(research §4.2). The header `ts` is server clock; the latency badge uses a
skew estimate `offset = min over 5 s window of (clientNow − ts)` and shows
`clientNow − ts − offset` (relative latency growth, robust to clock skew) —
implemented in `src/lib/time.ts`.

`onStats` is throttled to ≤4 Hz and writes only small numbers/flags into the
store. **Pixels never touch React state or zustand** (research §4.2).

### 5.5 Worker + OffscreenCanvas fallback

If profiling shows main-thread jank at 6×30 fps (research §7 flags this as
"profile once"), `VideoStream` supports `useWorker: true`: the component calls
`canvas.transferControlToOffscreen()` and posts `{canvas, url}` (transferring
the canvas) to `videoWorker.ts`, which runs the *same* WS + parse + 
`createImageBitmap` + `ctx.drawImage` loop entirely off the main thread and
posts stats messages back. Enabled globally via `?worker=1` query flag or
per-build env `VITE_VIDEO_WORKER=1`; default off in v1. The worker shares
`binary.ts`/`reconnecting.ts` (both DOM-free) — keep them import-clean.

## 6. Keyboard capture (`src/input/`)

### 6.1 Bindings source of truth

The canonical keymap lives in `core.protocol.keymap` and is fetched from
`GET /api/keymap` at app start (overview §5). The UI **builds its `BOUND` set
from the fetched keymap** — no hardcoded duplicate. Capture cannot be armed
until the keymap has loaded. `src/input/bindings.ts`:

```ts
export interface Bindings {
  bound: ReadonlySet<string>;                       // every code we preventDefault
  held: ReadonlySet<string>;                        // kind === "held"
  discrete: ReadonlyMap<string, ActionName>;        // code → action
  byGroup: ReadonlyMap<KeymapEntry["group"], KeymapEntry[]>;  // overlay rendering
}
export function buildBindings(entries: KeymapEntry[]): Bindings;
export function actionFor(code: string): ActionName | null;
```

Expected canonical entries (overview §5): `KeyW/KeyS` = translate ±x,
`KeyA/KeyD` = translate left/right, `KeyE/KeyQ` = up/down, `KeyI/KeyK` = roll
±, `KeyJ/KeyL` = pitch ±, `KeyU/KeyO` = yaw ±, `KeyF/KeyH` = gripper
close/open (held), `ArrowLeft/ArrowRight` = rail (held, `requires_rail:
true`), `Tab` = switch_arm, `Space` = takeover_toggle, `KeyN/Enter/Backspace`
= episode new/save/discard (all discrete).

Rail keys — **confirmed as designed (binding, spine v0.3)**: they are always
in `bound` (so arrows never scroll while capturing) and are included in `held`
messages regardless; **filtering is server-side** (the server ignores rail
input for non-rail arms). The UI's job is only to hide them from the hint
overlay when the active arm has `rail_pos_m === null` (§9 `KeymapOverlay`).

### 6.2 `useKeyCapture` hook

Explicit click-to-arm capture surface (noVNC pattern, research §4.1). Held
state lives in a `useRef<Set<string>>` — never React state (transitions happen
faster than render cycles need to know).

```ts
export interface KeyCaptureApi {
  armed: boolean;
  arm(): void;            // called by TeleopSurface click
  disarm(): void;         // Escape, click-away, programmatic (WS loss)
  heldRef: React.RefObject<ReadonlySet<string>>;
}
export function useKeyCapture(opts: {
  bindings: Bindings | null;               // null → hook inert
  onHeldChange: () => void;                // → control.notifyTransition()
  onAction: (name: ActionName) => void;    // → control.sendAction(name)
  onArmedChange: (armed: boolean) => void; // → control.setArmed(armed)
}): KeyCaptureApi;
```

Behavior (each line is a vitest case, §11):

- Listeners on `window` (`keydown`, `keyup`) registered only while armed.
- `keydown`: if `!bindings.bound.has(e.code)` → ignore (browser default runs).
  Else `e.preventDefault()` **always** (this is what stops Tab from moving
  focus, Space from scrolling, arrows from scrolling), then `if (e.repeat)
  return` (motion derives from held state, never OS auto-repeat), then:
  discrete code → `onAction(actionFor(code))` (once per physical press);
  held code → add to `heldRef`, `onHeldChange()`.
- `keyup`: `preventDefault` if bound; discrete codes are no-ops on keyup.
  **Resolved (binding, spine v0.3)**: Space is a **discrete takeover toggle**
  sent as `ActionMsg{name:"takeover_toggle"}` once per physical press — not a
  held dead-man key; it never appears in `held`. Held codes → delete from
  `heldRef`, `onHeldChange()`.
- **Release-all** — clear `heldRef` + `onHeldChange()` (which sends an
  immediate empty `KeysMsg`) + `disarm()` on: `window` `blur`,
  `document.visibilitychange` → hidden, `Escape` keydown, component unmount,
  control-WS status ≠ open.
- Browser-owned chords (`Ctrl+W`, `Ctrl+T`) cannot be intercepted — never
  bound; the keymap contains none.
- While a form element has focus (episode label inputs on the landing page),
  capture is by construction not armed — arming requires clicking the
  `TeleopSurface`, and any focus shift fires `blur`-path disarm on the surface.

### 6.3 Gamepad adapter (`src/input/gamepad.ts`, 13-tracker §5)

`GamepadAdapter` polls `navigator.getGamepads()` at 50 Hz (`setInterval`,
`getGamepads` injectable). Normalizer: `mapping === "standard"` → buttons
0 A, 1 B, 4 LB, 5 RB, 7 RT (`value ≥ 0.5`), 14 DpadLeft, 15 DpadRight; any
other mapping is raw Linux joydev order → buttons 0 A, 1 B, 4 LB, 5 RB,
`axes[6]` D-pad x (−1 left / +1 right), `axes[5]` RT (−1..1 or 0..1; the
adapter tracks the observed minimum to pick the threshold). Label → row comes
from `Bindings.gamepad` (built from `KeymapEntry.gamepad`); labels absent from
the served keymap are never injected. Held rows → codes in the adapter's held
set, discrete rows → `sendAction` once per press edge.

`clients.ts` no longer has a single held slot: `registerHeldSource(id, fn)` /
`setHeldSource(fn)` (= the `"keyboard"` slot) feed `heldUnion()`, which every
`KeysMsg` carries; `setArmedSource(id, armed)` keeps the 40 ms heartbeat
running while ANY source is armed. The first mapped press auto-arms the
`"gamepad"` source when the control link is open and the role is controller;
release-all (clear held + empty-set transition + disarm) on
`gamepaddisconnected`, `blur`, hidden `visibilitychange`, control link ≠ open
and unmount. `useGamepad()` mounts one adapter (Cockpit and Devices pages) and
mirrors its snapshot into `store.gamepad` (only on change). The armed state is
shown by the existing CAPTURING chip plus a blue GAMEPAD chip.

## 7. State management — zustand

**Decision: zustand v5** (research §4.2 concurs). Reasons: (1) WS handlers
write from *outside* React with plain `store.setState` — no dispatch
ceremony; (2) selector-based subscriptions keep 20–30 Hz telemetry cheap —
only components selecting a changed slice re-render, and hot numeric readouts
can use `store.subscribe` with a ref for render-free updates; (3) ~1 kB, no
provider nesting; Redux adds boilerplate for zero benefit at this scale, and
React context alone would re-render whole subtrees at telemetry rate.

Single store, flat slices (one file — the app is small):

```ts
interface AppState {
  // session
  session: SessionInfo | null;
  workcell: WorkcellStatus | null;
  keymap: KeymapEntry[] | null;
  bindings: Bindings | null;
  // live
  telemetry: TelemetryMsg | null;           // last full snapshot (replaced wholesale)
  telemetryAt: number;                      // performance.now() stamp
  telemetryStale: boolean;
  conn: { control: WsStatus; telemetry: WsStatus; role: "controller" | "observer" | null };
  captureArmed: boolean;
  video: Record<string, { stale: boolean; fps: number; latencyMs: number | null }>;
  toasts: Toast[];
  // actions (all plain functions; WS clients call these)
  setTelemetry(msg: TelemetryMsg): void;
  setConn(k: "control" | "telemetry", s: WsStatus): void;
  setVideoStats(id: string, s: AppState["video"][string]): void;
  resetForEpochChange(): void;              // clears session + telemetry, used by §5.1
}
export const useStore = create<AppState>()(...);
```

Derived selectors (exported helpers): `selectActiveArm`, `selectArm(armId)`,
`selectCollision`, `selectEpisode`, `selectDagger`, `selectInference`,
`selectControlLinkDown = (s) => s.conn.control !== "open"`.
Video pixel data and the held-key set are deliberately **not** in the store.

Threading model of the browser app: everything except the optional video
workers runs on the main thread — React rendering, WS JSON handling, the 40 ms
heartbeat timer, `createImageBitmap` *initiation* (decode itself is off-thread
in the browser). The design keeps per-message work O(small): telemetry handler
does one `setState`; video handler does header parse + bitmap decode + one
`drawImage`.

## 8. Pages

### 8.1 Landing (`pages/Landing.tsx`)

Loads on mount: `getWorkcell()`, `getCameras()`, `getScenes("sim")` or
`getScenes("twin")` per kind, `getProfiles()`, `getKeymap()`. Layout top to
bottom:

1. **Mode-of-workcell indicator + toggle** (`WorkcellKindToggle`): shows
   `workcell.kind` from config. **Confirmed (binding, spine v0.3)**: when both
   hardware and sim configs are available, `POST /api/session` **honors** the
   toggle choice; if runtime config only supports one kind the other option is
   disabled with a tooltip.
2. **Camera preview grid** (`CameraPreviewGrid`): exactly **4 slots** (overview:
   up to 4 cameras — 3 wrist + 1 env, typically 2 live). Each slot: a
   `StreamView` subscribed to `/ws/video/{camera_id}` for enumerated cameras
   with `live: true`; non-live slots render an empty state ("No camera").
   **Resolved (binding, spine v0.3)**: the runtime **does** serve real-camera
   streams pre-session, throttled to **~15 fps** for landing previews (full
   configured rate applies once a session starts). The UI needs no
   special-casing beyond `showLatencyBadge: false` on landing tiles.
3. **Per-arm status cards** (`ArmStatusCard` ×1–3): connectivity (green/red +
   IP), rail (detected 0–0.65 m / none — from §7 overview auto-detection),
   gripper (`xarm` | `xarm_g2` + force-capable badge | none), error code if
   nonzero. Each card has an **"include in session"** checkbox (arm selection)
   and, when included, a **recording-frame selector** (`FrameSelector`):
   options `arm_base` (serialized `arm_base:<this arm's id>`), `world`, and
   `camera:<id>` for each enumerated camera. Default `arm_base`.
4. **Scene pickers** (`ScenePicker`): sim mode → sim scene (required);
   hardware mode → **digital-twin scene** (required — the twin gate is the
   authoritative safety layer, overview §6; the UI refuses to submit a
   hardware session without one). Picker rows show scene metadata (#arms, rail
   flags) and disable scenes whose arm count mismatches the selection.
5. **Start-from + profile picker** (`ProfilePicker` + `StartFromChoice`):
   every session declares `start_from` (spine §3.4). A two-option radio:
   **"Keep current state"** (default; arms stay exactly where they are) vs
   **"Load selected profile"** (twin-planned safe motion). The profile list is
   enabled only when the second option is chosen; rows show name, covered
   arms, notes, and a **"initial condition" badge** on the one profile with
   `is_initial_condition: true` (the designated workcell initial condition,
   preselected by default when "Load selected profile" is picked). Profiles
   covering arms not in the selection are disabled. Loading happens
   server-side via the twin planner during session start — the UI passes
   `start_from: "keep_current" | "profile:<id>"` in `SessionSpec` and shows a
   "Loading profile — planning safe path…" progress state until the POST
   returns.
6. **Mode inputs + mode buttons**: a **task** text input (shown for
   Collect/DAgger — the dataset task string, `SessionSpec.task`) and a
   **policy** selector (shown for DAgger/Inference; populated from
   `GET /api/policies`; DAgger defaults to "latest", Inference defaults to
   the promoted deploy checkpoint and lists only `promoted` entries). Then
   Teleop / Collect / DAgger / Inference buttons → `createSession` with the
   assembled `SessionSpec` (including `kind` from the workcell toggle), then
   navigate to `#/<mode>`.

Validation before submit: ≥1 arm selected; every selected arm has a frame
choice; scene picked per kind rules; a `start_from` value is always present
("Load selected profile" requires a profile to be selected); Collect/DAgger
require a non-empty `task`; DAgger/inference additionally require the
runtime to report an available policy
(`WorkcellStatus.policies_available`, else the buttons are disabled with a
reason tooltip — inference further requires a promoted deploy checkpoint).

- **Video panes**: one `StreamView` per id in `session.streams` — real
  cameras, the sim render (`"sim"`), and the digital-twin render (`"twin"`)
  are uniform streams (overview §8; ids `"sim"`/`"twin"` are **confirmed
  reserved** — binding, spine v0.3); no special-casing in the UI.
- **TeleopSurface** wraps the grid: `tabIndex={0}`, click to arm, unmistakable
  armed state (2 px accent border + pulsing "CAPTURING — Esc to release"
  chip). Present in **all four** modes. In inference (spine v0.3 §4.4) the
  surface is live so **Space toggles human takeover as a safety escape**:
  movement keys stream as usual when armed, and the server applies them only
  while `control_mode === "human"` (policy-driving frames ignore them).
  A standing chip reads "Policy driving — Space = takeover (safety escape)".
- **KeymapOverlay**: table grouped by `KeymapEntry.group`, driven entirely by
  the fetched keymap, with three glyph columns: keycap, gamepad
  (`KeymapEntry.gamepad`) and Vive controller (13-tracker §1.1; the served
  keymap has no controller field, so the glyph comes from the static
  `CONTROLLER_GLYPHS` table in `input/bindings.ts` keyed by *action*:
  `tracker_clutch` → `trigger`, `gripper_open` → `pad ▲`, `gripper_close` →
  `pad ▼`, dash otherwise). Rows with `requires_rail: true` render only when the
  *active* arm has a rail. Rows for `group === "episode"` render only in
  collect/dagger; the `takeover_toggle` row renders on **both DAgger and
  inference pages with two different semantics labels** (spine §5): dagger —
  "takeover toggle (recorded as intervention)"; inference — "takeover toggle
  (safety escape — never recorded)". The mode-specific label is chosen
  client-side from `mode`; all other labels come from the keymap `label`
  (server-defined); the physical keycap hint uses `event.code`-derived names
  ("W", "Space", "←").
- **CollisionBanner + ClearanceReadout**: `severity === "warn"` → amber banner
  "CLEARANCE LOW arm0/link5 ↔ arm1/link3 (12 mm)"; `"blocked"` → red banner
  "COMMAND BLOCKED BY TWIN GATE" + the offending pair; `StreamView` tiles of
  the twin/sim get a flashing border while blocked. `ClearanceReadout` lists
  the k=5 smallest `clearances` in mm, monospace, color-graded.
- **ArmIndicator**: active arm id (from telemetry, server-authoritative),
  per-arm chips with rail position (m, 3 decimals) and gripper fraction; Tab
  hint. Non-active included arms show "holding".
- **EpisodeControls** (collect/dagger only): reflects
  `telemetry.episode.state`; three buttons mirroring N/Enter/Backspace.
  `idle`: only "New episode (N)" enabled. `recording`: "Save (Enter)" +
  "Discard (Backspace)" enabled, red REC dot + frame count + duration.
  `saving`: all disabled, spinner. Buttons call `control.sendAction(...)` —
  same path as keys; optimistic UI is *not* used (state flips when telemetry
  confirms).
- **DaggerPanel** (dagger only): big control-mode chip — `policy` (blue,
  "POLICY DRIVING"), `human` (green, "HUMAN TAKEOVER — recording
  intervention"), `takeover_transition` (amber, "TRANSITION — frames
  unlabeled"); `policy_version` (checkpoint tag, updates at episode boundaries
  per overview §4.3); labeled-episode counter; Space hint.
- **InferencePanel** (inference only): reads `telemetry.inference`. Takeover
  indicator with **safety-escape semantics — visually distinct from DAgger's
  recorded-intervention indicator**: `human` renders as a red/hazard-striped
  chip "SAFETY ESCAPE — NOT RECORDED" (never green, never a REC glyph — no
  frame from this mode is recorded or fed to DAgger aggregation, spine §4.4);
  `policy` renders the blue "POLICY DRIVING" chip. Below it, a **"Terminate
  session"** button (calls `DELETE /api/session`, then navigates to `#/`):
  normal-weight destructive styling while policy drives (with a confirm
  dialog), but **emphasized during takeover** — enlarged, solid red, confirm
  dialog skipped — because the spine's escape playbook is "steer to safe,
  then terminate", and that path must be one click.

Mode pages differ only in: which side panels render, the TeleopSurface's
mode-specific chrome, and the page title. That is the whole diff —
`Teleop.tsx` etc. are ~15-line wrappers.

### 8.3 Direct joint-control panel (Teleop page only)

`JointPanel` renders in the Cockpit side-panel slot on `#/teleop` (overview
§4.1: direct joint control is a teleop-mode facility). It targets the
**active arm** (server-authoritative, same arm Tab drives).

- **Rows**: one slider + numeric entry per joint for **all 7 joints**, plus a
  **rail row** (slider 0–0.65 m + numeric) rendered only when the active arm
  has a rail (`rail_pos_m !== null`); **hidden entirely when absent** — no
  disabled placeholder. Slider ranges come from `ArmStatusInfo.joint_limits`.
- **Jog (sliders)**: drags are throttled to **~20 Hz** (50 ms trailing
  throttle); each send is `ActionMsg{name:"joint_target", args:
  {arm_id, positions, mode:"jog"}}` with the full positions vector (rad ×7,
  rail meters appended for rail arms). Server-side these stream through
  slew-limited joint servo behind the twin gate (overview §4.1, §6).
- **Go-to (numeric entry)**: typing values and pressing the **"Go to"**
  button (or Enter in a field) sends one `joint_target` with `mode:"goto"` —
  a twin-planned motion. The panel shows the lifecycle from
  `ArmTelemetry.goto`: **planning** (spinner on the button) → **executing**
  (progress shimmer; sliders track telemetry) → **failed** (red row flash +
  toast with `AckMsg.detail` / planner reason). An `AckMsg{ok:false}` surfaces
  immediate rejection the same way.
- **Recording lock**: the entire panel is disabled (inputs inert, greyed,
  "recording — panel locked" tooltip) while
  `telemetry.episode?.state === "recording"`.
- **Seeding**: slider/numeric values are seeded from telemetry (`q`,
  `rail_pos_m`) whenever the operator is not interacting; a row being dragged
  or edited is user-owned until pointer-up / blur, then re-syncs to telemetry.
- **Highlight-on-limit**: a row turns amber when its commanded or measured
  value is within 2% of either end of its `joint_limits` range (rail: 0 or
  0.65 m).

**Profile actions (Teleop side panel, `ProfileActions`)**: "Save profile…"
(names + notes dialog → `ActionMsg{name:"save_profile", args:{name, notes}}`)
and **"Set current state as initial condition"** — overwrites the designated
initial-condition profile (spine §3.4) with the current workcell state, behind
a **confirm dialog** ("Overwrite '<name>' as the workcell initial condition?")
since it is destructive; sends `ActionMsg{name:"set_initial_condition"}` and
confirms via `AckMsg` + a toast.

### 8.4 Devices page (`#/devices`, 13-tracker §5)

No session loader — device panels work before any session exists. Layout:
main column = header (link back to `#/`), `ConnectionBanner`, GAMEPAD ARMED

  default, auto-opens when a pad connects, manual toggle otherwise; the adapter

  `telemetry.tracker.controller` / `.device_held`): "controller: none" grey chip

  trigger analog bar (0..1, `role=progressbar`) + `pressed` chip, a trackpad

  idle/touch/click tones), `touch`/`click` chips and the numeric x/y, grip /
  menu / system chips (menu + system flagged as the pairing combo), and the
  injected codes: one chip per `CONTROLLER_GLYPHS` action (`trigger →
  tracker_clutch (C)`, `pad ▲ → gripper_open (H)`, `pad ▼ → gripper_close (F)`)
  lit while its served-keymap code is in `device_held`, plus a raw lit chip for
  any unexpected code. A stale sample arrives with `device_held: []`, so every
  action chip goes dark while the raw button state stays visible.
- `TrackerPanel`: status chip (tracking green / searching·starting·stale amber /
  error red / no_backend grey), clutch chip (`CLUTCH · <arm>` or `released`),
  backend · object · seq · rate · age, `detail`, raw/world/anchor/target pose
  rows (m, wxyz), a large world-z readout and `TrackerTrail` — a 2-D top-down
  canvas (x right, y up, autoscaled, equal aspect) fed from
  `useStore.subscribe` into a ~5 s × 25 Hz ring buffer (never React state),
  drawing the `pose_world` trail plus the anchor ring and target cross while
  the clutch is engaged.
- `TrackerSettingsForm`: `yaw_deg` / `pos_scale` numbers and a
  `follow_rotation` checkbox → `sendAction("tracker_settings", {field})` on
  change (numbers only when finite; `pos_scale` only within 0.1–3); fields the
  operator is not editing follow the echoed `telemetry.tracker.settings`.
- `SessionControls`: no session → "Start teleop · sim · mavis_v2" (`POST
  /api/session` with arms `view`,`grip`, frames `arm_base:<id>`); session →
  mode · scene (known only when started here) · arms · state + Stop
  (`DELETE /api/session`).

## 10. Empty / error / degraded states

| Condition | Detection | UI behavior | Recovery |
|---|---|---|---|
| Control WS down | `conn.control !== "open"` | Full-width red banner **"CONTROL LINK DOWN"**; capture force-disarmed; episode buttons disabled | `ReconnectingWS` backoff; on open: hello → epoch check → `GET /api/session` resync → resume from all-keys-up; operator re-arms manually |
| Runtime restarted (epoch change) | hello `epoch` ≠ stored | Toast "Runtime restarted — session lost"; `resetForEpochChange()`; navigate `#/` | Operator starts a new session |
| Second tab holds control | hello `role === "observer"` | Amber banner "Another tab holds control — read-only"; capture disabled; video + telemetry still live | Close the other tab; reconnect promotes |
| Telemetry stale | `now − telemetryAt > 1000 ms` | Side-panel values grey out + "TELEMETRY STALE" chip; collision banner shows last-known + "(stale)" | Auto on next message |
| Video frame stale | no drawn frame for 500 ms | Tile greys, "STALE" chip, last frame kept visible (context beats black) | Auto on next frame |
| Video WS closed | per-stream status | Tile empty state "Stream unavailable — retrying…" + spinner | Per-stream reconnect backoff |
| Arm disconnected mid-session | `ArmTelemetry.connected === false` | Arm chip red in `ArmIndicator`; banner "arm1 DISCONNECTED — motion held"; capture stays armed (server holds that arm) | Runtime reconnect/recovery (overview §6 watchdogs); chip greens on telemetry |
| Arm error code ≠ 0 | telemetry | Chip shows code + short text; tooltip "runtime auto-recovers: clean_error → motion_enable → set_mode → set_state → re-seed" | Server-side |
| Joint goto failed | `ArmTelemetry.goto === "failed"` or `AckMsg{ok:false}` for `joint_target` | JointPanel row flash red + toast with planner reason; values re-seed from telemetry | Cleared by server on next command; operator retries |
| Collision blocked | `collision.severity === "blocked"` | Red banner + pair names; twin tile border flash; clearance rows red | Clears via telemetry when commands pass the gate |

| DAgger, no policy | `WorkcellStatus.policies_available === false` | DAgger/Inference buttons disabled + tooltip | — |

## 12. Cross-doc contract points (must match `04-runtime.md`)

Points 1–6 are **CONFIRMED as designed** (binding, spine v0.3); 7–10 were
added by this amendment.

1. `GET /api/keymap` returns `KeymapEntry[]` from `core.protocol.keymap`. ✔
2. Control WS: server sends `HelloMsg` immediately after accept; `AckMsg` per
   `ActionMsg`; single-writer with observer fallback (close 1008 alternative
   is *not* used — observer role is). ✔
3. Episode ops + profile ops (`save_profile`, `set_initial_condition`) ride
   the control WS as `ActionMsg` (not REST). ✔
4. Video binary layout `<dI` header (12 bytes) + JPEG; stream ids = camera ids
   plus reserved `"sim"` / `"twin"`; camera preview streams available
   pre-session for the landing grid at **~15 fps**. ✔
5. Rail held-keys are always sent; server-side filtering ignores them for
   non-rail arms. ✔
6. Active arm is server-authoritative; `switch_arm` carries no index. ✔
   (Dev port 8765 and the hardware/sim toggle honored by `POST /api/session`
   when both configs exist are likewise confirmed — §1.1, §8.1.)
7. `joint_target` `ActionMsg` (`{arm_id, positions, mode:"jog"|"goto"}`):
   jog = slew-limited servo, goto = twin-planned; goto lifecycle surfaces as
   `ArmTelemetry.goto` (`planning|executing|failed|null`); rejected while an
   episode is recording (`AckMsg{ok:false}`).
8. `SessionSpec.start_from: "keep_current" | "profile:<id>"` replaces the old
   optional `profile` field (spine §3.4).
9. `ProfileInfo.is_initial_condition` flags the one designated
   initial-condition profile; `set_initial_condition` overwrites it from the
   current workcell state.
10. Inference telemetry carries `InferenceStatus{control_mode, engaged_arm,
    policy_version}` (same TakeoverGate as DAgger); Space is a discrete
    `takeover_toggle` `ActionMsg` in both modes — recorded intervention in
    DAgger, safety escape (never recorded) in inference;
    `ArmStatusInfo.joint_limits` is served for the joint panel.
