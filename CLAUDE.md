## Rules that protect the cell

- **No implicit motion.** `connect()` never homes a track; `home_rail` (Hardware-tab arm card, twin-gated, session-less) is the ONLY motion-class maintenance op. Error clearing, `apply_backstops`, `recover` and `set_collision_sensitivity` (operator's 1 / 2 / 3 level; volatile — the config value 3 returns at the next connect) produce NO motion; their raw uxbus 1 / 2 / 9 replies are status echoes, not failures (02-hardware §16). Teardown leaves the arms stopped with brakes engaged; tracks keep their homed state.
- **`hardware_session.armed` gates every real driver connection.** Repo config `false`; only a RENDERED config arms it (`render-lab-config.sh HARDWARE_ARMED=true`, or `mavis-dev.sh render` with the gitignored `scripts/dev/local.env`). Never set `armed: true` in a tracked config. Never run the runtime test suite on the lab machine without the `tests/conftest.py` guard (04-runtime §16).
- **Never `uv run` in a sub-repo whose venv a live runtime is executing from** — it re-syncs and REINSTALLS the package under the running process, which on 2026-09-10 killed the dev runtime mid hardware session with the arms left enabled and no teardown. Stop the runtime first (`mavis-dev.sh stop runtime`), or use a separate worktree; never with a session open, never two test runs in one tree at once (DEPLOYMENT S11). The venv's own entry points (`.venv/bin/pytest`, `.venv/bin/python -m …`) do NOT re-sync — with a runtime live, call those instead of `uv run`. (A `uv sync` in the runtime dir also drops the out-of-lock pysurvive wheel — re-install from `third_party/wheels/`; DEPLOYMENT S2.)
- Never open UFACTORY Studio "Live control" during a session. Controller `state 2` (standby) is HEALTHY for a mode-1 arm holding a posture (02-hardware §16).
- A hardware session always includes BOTH arms; the default active arm is ALWAYS the Manipulation Arm (hardware and sim).
- **Twin-planned multi-arm motions execute ONE ARM AT A TIME in the planner's `arm_order`** (`SessionManager._execute_arms`: return phases, per-episode return, `start_from`, `goto_profile`).
- **A plan from inside the inflation shell starts with an OPENING escape mirroring the gate's T8 rule** (11-safety §9, 03-sim §10). Never whitelist a violating pair in the planner — the gate is the safety authority.
- **The twin does NOT model the room the cell sits in (03-sim §4.5):** the blue cart with the toy food and the whole kitchen run of §4.4 are absent from `mavis_v2` — the scene the gate, the planner AND the overlays use. The gate is therefore blind there: a twin-planned, gate-approved `return_home` was cancelled twice by `controller error 31 Collision Caused Abnormal Current` (2026-09-09, 03-sim §4.5). Until the cart and the appliances are in the scene, treat every planned motion (return-to-start, `R`, `goto_profile`, `home_rail`) as unverified: 10 % speed, hand on the E-stop. The arms and rails themselves are ~15–30 mm out in the twin (03-sim §4.5 addendum) — that is why the shell is 25 mm (`geom_inflation_m`, a STOP-GAP: re-measure the cell and bring it down); the `view_wrist` `[21, 13]` nudge is a depth-dependent patch, not a real per-arm extrinsic. Judge alignment only at a posture where the twin predicts geometry in frame.
- Driver caps at scale 1.0: `max_joint_vel` 0.6 rad/s, `max_cart_step_m` 0.004, rail 50 mm/s — never raise the cart step without re-checking it against the gate shell. Hardware tab picks 10 / 50 / 100 %, default 100 % (operator decision).
- A recoverable fault re-firing within 1.5 s of an auto-recovery with no new target LATCHES at once (`REFAULT_WINDOW_S`): back the load off or let go, then Recover (02-hardware §3.5). The fridge door's seal / hinge torque is a real external torque and sensitivity 3 reads it as a collision; dropping the Manipulation Arm to 2 (then 1), weighing the payload and pulling along the door's arc are the OPERATOR's calls.

## Live risks (2026-09-12) — policy-driven motion on the real arms

- **`hardware_session.policy_modes` (operator decision 2026-09-12) admits `inference` / `dagger` and action-column playback on the REAL arms.** Repo default `false`; ON in the lab (`var/lab.env: HARDWARE_POLICY_MODES=true`). With it false the 409 names the knob. Same gated stack as sim — the twin `SafetyGate`, the executor leash / SlewLimits and the driver caps are unchanged (04-runtime §5/§11, 15-online-dagger D7 + §12, 11-safety §4).
- **Policy-driven motion on hardware runs at 10 % with a hand on the E-stop until it is trusted** — the twin is still 15–30 mm out and blind to the cart / kitchen. Episode replay through the policy path was trialled 2026-09-12 03:01–04:11 (grip driven, view holding, `gate=ok`); a TRAINED-policy session is still unrun.
- Inference over dora works for `delta_ee` and `abs_ee`; per-arm `action_<arm>` streams are primary and an arm no policy claims HOLDS (14-dora v1.3/v1.4, 04-runtime §11). The executor integrates on the LAST COMMAND and applies each action row exactly once — never re-anchor a delta to the measured pose (04-runtime §11, 12-dagger §6).
- Action replay does not retrace the recorded path: in sim `abs_ee` tracked ~2× tighter than `delta_ee` (6.7 vs 14.5 mm RMS; numbers + harness in 12-dagger §6), and the residual is the TWIN's servo bandwidth, not the executor — never retune the twin's `kp` (03-sim §6). Playback takes `source: state | delta_ee | abs_ee`; the action sources need `policy_modes` on hardware (04-runtime §10.8).
- **Replaying an action column through the external dora path: the publish rate must scale WITH `speed_scale`.** The runtime spreads one `delta_ee` row over one ANNOUNCED period (`period = 1/rate_hz`), so the per-tick joint demand is `row × rate_hz/100` against a cap of `dq_max × speed_scale`. Rule of thumb `rate_hz ≈ fps × speed_scale` with node `--speed ≈ speed_scale`: at 25 fps and `speed_scale` 0.1, `--rate-hz 30` gives 159 mm position RMS in sim and `--rate-hz 2.5–3` gives 14.8 mm. **Do NOT reach for `--chunk-dt-s`** — for `delta_ee` the runtime rescales each row by `period/chunk_dt`, so total travel is multiplied by `1/(rate × chunk_dt)`, and for `abs_ee` `chunk_dt` never enters the path. **This is a REPLAY artifact, not a policy requirement**: a replay is open-loop in time (frame `k` advances on a clock, so unachieved motion piles up) while a policy is closed-loop (it reads `obs_state` and acts from the measured pose), so a trained policy needs no rate scaling — it only has to ANNOUNCE its true `rate_hz`, and `chunk_dt_s` honestly if one row is worth more than one period (a 25 fps-trained delta row published at 30 Hz runs 20 % fast otherwise).
- **`abs_ee` is robust to a reduced `speed_scale`, `delta_ee` is not**: an absolute waypoint keeps converging when a cap delays the arm, while a capped delta row is dropped forever (the next tick anchors on `FK(q_last)`). First hardware measurements 2026-09-12 (`bc_demo/lamp_assembling` `20260911T214721.850Z-7b6028`, Manipulation Arm alone, `speed_scale` 0.6 / node speed 0.5 / rate 15): `abs_ee` 5.0 mm RMS and 0.0 mm final, 11.7 mrad RMS and 0.01 mrad final; `delta_ee` 4.1 mm RMS but 195 mrad rotation RMS, injecting 267 mrad of tool rotation where the recording had 45 — an **OPEN `delta_ee` rotation defect, hardware-only** (sim 18.8 mrad). It is a smooth DRIFT, not a jump: the largest single-observation change is 9 mrad (mean 1.3), which is why it looks fine at the cell. Mechanism: `delta_ee` anchors on the last COMMAND (`FK(q_last)`, already cap- and gate-clipped) with no absolute orientation reference to pull the residual back, so every clipped tick accumulates; `abs_ee` erases the residual on every row (error bounded at 42 mrad, back to 0 at the end). **Prefer `abs_ee` on the real arms**, and never lower `speed_scale` on a `delta_ee` policy.

- `grep 'loop:' var/logs/runtime.log` — the 1 Hz health line (fields, incl. `dq_capped` / `leash_slips` / `ik_slips` / `watchdog`, in 04-runtime §14 "Logging"); `var/logs/runtime.stderr.log` holds libsurvive / MuJoCo prints.
- Joint panel dead while Vive works ⇒ `watchdog=LATCHED` next to `src=joint_jog` (11-safety §10.1). Buttons dead while poses flow ⇒ restart the runtime, not the controller (13-tracker §3 item 7b).
- Arm NICs `unavailable` = no carrier = physical, not software (DEPLOYMENT "arms unreachable").
- A running runtime never picks up config or code changes — restart it (the one place this file needs to say so).
